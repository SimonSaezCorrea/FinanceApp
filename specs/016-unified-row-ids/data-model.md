# Data Model: Unified Row Identifiers

This feature introduces no new table and no new business entity. It changes how an existing
concept — the row identifier — is generated and validated. Documented here for completeness
(the spec's Key Entities section already names both).

## Row identifier

- **What it is**: the `id String @id` column present on all 24 tables in
  `apps/api/prisma/schema.prisma`.
- **Before**: `@default(cuid())` on every table, but 5 write paths mint their own id with
  `randomUUID()` (a v4 UUID) instead of using the schema default — two formats coexist across the
  schema.
- **After**: `@default(uuid(7))` on every table; the 5 write paths mint their id via one shared
  application helper producing the same UUID v7 format. No table is exempt.
- **Format**: RFC 9562 UUID version 7 — 36-character canonical string
  (`xxxxxxxx-xxxx-7xxx-Nxxx-xxxxxxxxxxxx`, version nibble fixed at `7`).
- **Validated**: at every API boundary point where a caller supplies one — a path parameter, or a
  body field referencing another row — via the shared `rowId` zod schema (see Contracts below).
  Never validated as "any string" again.
- **Not affected**: the values already stored in a developer's local database under the old format
  — no migration; a fresh `db push && db seed` produces a database where 100% of ids are UUID v7
  (SC-001).

## Business identifier (unaffected, documented for contrast)

- **What it is**: domain-meaningful identifiers already modeled as their own columns — e.g.
  `FinancialInstitution.code` (SBIF/CMF/`RUT-`/`PSP-`/`AGF-`), `BankAccount.accountNumber`/
  `accountAlias`, a country's ISO codes.
- **Relationship to the row identifier**: none — never the primary key, never generated by the
  mechanism this feature touches, already carries its own validation (e.g. `isValidCbu`).
  Explicitly out of scope (spec FR-006, Edge Cases).

## Application-minted id sites (the 5 write paths, unified to the same generator)

| File                                                                           | Field                  | Current call   | New call             |
| ------------------------------------------------------------------------------ | ---------------------- | -------------- | -------------------- |
| `credit-statement/application/commands/pay-credit-statement.handler.ts:126`    | `paymentTransactionId` | `randomUUID()` | shared row-id helper |
| `installment-plan/application/commands/pay-installment.handler.ts:126`         | `transactionId`        | `randomUUID()` | shared row-id helper |
| `transaction/application/commands/create-transfer.handler.ts:65`               | `transferGroupId`      | `randomUUID()` | shared row-id helper |
| `transaction-attachment/application/commands/upload-attachment.handler.ts:61`  | `attachmentId`         | `randomUUID()` | shared row-id helper |
| `installment-plan/application/commands/create-installment-plan.handler.ts:196` | plan's own `id`        | `randomUUID()` | shared row-id helper |

Note: `transferGroupId` is not itself a table's primary key (it's a correlation value shared by two
`Transaction` rows) but is minted the same way for the same reason — one identifier format across
the whole system, no carve-out for non-PK identifier-shaped values either.

## Contracts — shared validation primitive

- **`rowId`** (new, `packages/contracts/src/common/row-id.ts`): `z.uuidv7()` tagged with
  `meta({ errorCode: "INVALID_ID_FORMAT" })`. Exported and reused by:
  - The 13 path-param schema files under `apps/api/src/domains/*/presentation/dto/*.params.ts`
    (their id-shaped fields only — `installmentPaymentParamsSchema.seq` stays a coerced integer).
  - Every domain schema field in `packages/contracts/src/**` that references another row by id
    (the ~62 figure from the constitution's audit): `bankAccountId`, `cardId`, `cardholderCardId`,
    `installmentPlanId`, `paymentAccountId`, `savingsGoalId`, `institutionId`, `countryId`,
    `creditStatementId`, and every other `*Id` field shaped this way across `accounts`,
    `transactions`, `installments`, `debts`, `savings`, `investments`, `recurring`, `wallet`,
    `reference` schemas.

## Error contract (no new shape, one new code)

- **Code**: `INVALID_ID_FORMAT` — added to the project's existing flat error-code vocabulary
  (`{ error: { code, field? } }`), alongside `CARD_REQUIRED`, `EMAIL_TAKEN`, etc. Not a new
  response shape.
- **Emitted by**: `ZodParamsPipe` (path params) and `ZodValidationPipe` (body/query) whenever the
  failing field is backed by `rowId` — both pipes gain the same small meta-tag check, no new pipe
  type.
- **es/en copy**: one new `errors.INVALID_ID_FORMAT` entry added to both
  `apps/web/src/i18n/es.json` and `en.json` (parity enforced by the existing
  `src/i18n/parity.test.ts`).

## FK ownership verification (User Story 4, added 2026-09-04)

- **`BankAccountLookupPort`** (new, `bank-account/domain/ports/bank-account-lookup.port.ts`):
  `accountOwned(userId, accountId): Promise<boolean>`. Adapter:
  `PrismaBankAccountLookupRepository` (`WHERE id = ? AND userId = ?`). Wired into the existing
  `BankAccountDataModule`, exported alongside the full `BankAccountRepositoryPort`.
- **Five write paths, now ownership-checked before persisting**:

  | Domain              | Field                                   | Handler(s)                                                                   | Error on mismatch                                                                                    |
  | ------------------- | --------------------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
  | `import`            | `bankAccountId` (per row, deduplicated) | `import-transactions.handler.ts`                                             | `AccountNotFoundError` (bank-account domain)                                                         |
  | `investment`        | `bankAccountId`                         | `create-investment.handler.ts`, `update-investment.handler.ts`               | `AccountNotFoundError`                                                                               |
  | `recurring-expense` | `bankAccountId`                         | `create-recurring-expense.handler.ts`, `update-recurring-expense.handler.ts` | `AccountNotFoundError`                                                                               |
  | `installment-plan`  | `paymentAccountId`                      | `create-installment-plan.handler.ts`, `update-installment-plan.handler.ts`   | `AccountNotFoundError` (reuses the already-injected full `BankAccountRepositoryPort.findById`)       |
  | `installment-plan`  | `cardId`                                | same two handlers                                                            | `CardNotFoundError` (bank-account domain) — was previously silently accepted when foreign, see below |

- **The `cardId` conflation fix**: `CardAccountRepositoryPort.kindForCard(userId, cardId)` already
  scoped its query by `userId`, so it always safely returned `null` for a foreign card — the actual
  bug was in the two `installment-plan` handlers, which read that `null` as "this plan has no card"
  and proceeded to persist the plan with the caller-supplied (foreign) `cardId` anyway. Fixed by
  checking `input.cardId && !cardKind` before applying the business rule that null cardKind
  otherwise correctly triggers.
- **Unaffected by this story**: `POST /transactions`'s `cardId` (already throws
  `CardAccountMismatchError` via `movement-policy.ts`) and `POST /wallet` (already has its own
  `accountOwned`/`cardOwned`) — both confirmed correct by inspection, not modified.
